# ADR-0001. Способ доставки кода на сервер

- Статус: принято
- Дата: 2026-10-11

## Контекст

TimeCapsule работает на одном экземпляре EC2 (Amazon Linux 2023) с nginx, PHP-FPM и PostgreSQL.
Код хранится в публичном репозитории `timecapsule` в организации GitHub.
Нужно выпускать новые версии так, чтобы:

- было видно, какая версия работает на сервере;
- нельзя было забыть файл или шаг;
- плохую версию можно было быстро откатить.

Ограничения: один сервер, нет CI/CD, есть только `git` и SSH.
Пароль к базе нельзя хранить в репозитории.

## Решение

Сервер сам забирает код из GitHub по HTTPS (только чтение).
Новая версия выпускается скриптом `~/deploy.sh` на сервере.
Скрипт выполняет `git pull --ff-only`, `composer install`, `php bin/init-db.php` и `systemctl reload php-fpm`.
Запускаем его со своего компьютера одной командой:

```bash
ssh -i ~/.ssh/<nickname>-keypair.pem ec2-user@<Public-IP> ./deploy.sh
```

Секреты лежат только на сервере в файле `.env`, который git не отслеживает.
Откат делается через репозиторий: `git revert`, `git push`, затем снова деплой.

## Рассмотренные альтернативы

- Копирование файлов через `scp` с ноутбука.
  Просто для трёх HTML-файлов.
  Для приложения плохо: не видно, какая версия на сервере, легко пропустить файл.
  Откат возможен, только если старая копия где-то сохранилась.
  `composer install` и создание таблиц всё равно нужно делать руками по SSH.
- `git pull` вручную на сервере (вариант A).
  Версия видна через `git log`, откат идёт через репозиторий.
  Но человек каждый раз набирает 4-5 команд и может пропустить одну.
  Например, забыть `composer install`, и сайт упадёт при новой библиотеке.
- Скрипт `deploy.sh` (выбрано).
  Те же шаги, что в варианте A, но всегда в одном порядке.
  `set -euo pipefail` останавливает скрипт на первой ошибке.
  Запуск одной командой по SSH, это уже основа для CI/CD.

## Последствия

- Плюс: один источник кода, это репозиторий. На сервере видна точная версия (`git log -1`).
- Плюс: деплой занимает одну команду, шаги не теряются.
- Плюс: сервер не может менять код в репозитории. Взлом сервера не даёт доступа к коду на GitHub.
- Минус: во время `git pull` и `composer install` сайт несколько секунд может отвечать с ошибкой.
  Файлы меняются по одному, атомарного переключения версии нет.
- Минус: нет автоматических проверок до деплоя. Сломанный код попадает на сервер, как в задании 13.
- Минус: `/health` проверяет только базу, поэтому сломанную страницу он не замечает.
- Риск: если на сервере кто-то поменяет файлы руками, `git pull --ff-only` откажется работать.
- Риск: всё на одном экземпляре. Если его удалить, пропадут база и загруженные файлы.
- Дальше: перенести эти шаги в CI/CD (GitHub Actions), добавить тесты перед деплоем
  и выкладку в новую папку с переключением ссылки (symlink), чтобы не было простоя.

# ADR-0002. Где размещать базу данных

- Статус: принято
- Дата: 2026-10-14
- Заменяет часть ADR-0001: база больше не живёт на сервере приложения.

## Контекст

В ЛР2 TimeCapsule и PostgreSQL работали на одном экземпляре в default VPC.
Все подсети default VPC публичные.
В ЛР3 у приложения своя сеть `timecapsule-dev-vpc` (`10.7.0.0/16`): две публичные и две приватные подсети в зонах `eu-central-1a` и `eu-central-1b`.
Нужно решить, где держать базу, чтобы:

- из интернета к ней не было пути;
- приложение находило её по имени, которое не меняется;
- данные пережили замену сервера приложения;
- это стоило мало, на уровне учебного бюджета.

## Рассмотренные варианты

- **На одном сервере с приложением (как в ЛР2).**
  Самый дешёвый и простой вариант: один экземпляр, база на `localhost`.
  Но сервер стоит в публичной подсети. Если взломают приложение, взломщик сразу получает и базу.
  Приложение и база делят CPU и память. Пересоздать сервер приложения, не трогая данные, нельзя.
- **На отдельном сервере в публичной подсети.**
  Приложение и база разделены, и `dnf update` работает всегда, без NAT.
  Но у базы есть публичный адрес и маршрут в Internet Gateway.
  От интернета её отделяет только Security Group, и одна ошибка в правиле открывает порт 5432 всему миру.
  За публичный IPv4 платим $0,005 в час.
- **На отдельном сервере в приватной подсети (выбрано).**
  У `db-server` нет публичного адреса, а в `private-rt` нет маршрута в интернет.
  Даже ошибка в Security Group не откроет базу из интернета: снаружи до неё нет пути.
  Доступ ограничивают три уровня: сеть, `db-sg` (5432 только от `web-sg`) и `pg_hba.conf` (только пользователь `timecapsule`, только из `10.7.0.0/24`, по паролю).
  Минус: для обновлений нужен выход в интернет, которого у подсети нет.
- **Amazon RDS** не рассматривался подробно: он появится в следующих работах.

## Решение

PostgreSQL 16 работает на отдельном экземпляре `timecapsule-dev-db` в подсети `timecapsule-dev-private-a`.
Приложение обращается к базе по имени `db.timecapsule.internal` из приватной зоны Route 53.
SSH на `db-server` идёт только через `timecapsule-dev-bastion`.

## Последствия

- Плюс: из интернета к базе нет ни адреса, ни маршрута. Это видно на проверке `curl` с `db-server`.
- Плюс: имя `db.timecapsule.internal` не зависит от адреса. Если `db-server` пересоздадут, правим одну запись `A` в зоне, а `.env` не трогаем.
- Плюс: сервер приложения можно пересоздать из образа, и база при этом не пострадает.
- **Обновления базы.** Постоянного выхода в интернет у `db-server` нет.
  Для `dnf update` поднимаем временный NAT Gateway скриптом `scripts/nat-up.sh`, ставим обновления и убираем его скриптом `scripts/nat-down.sh`.
  NAT Gateway во Франкфурте стоит около $0,052 в час и $0,052 за каждый ГБ трафика. Elastic IP шлюза стоит ещё $0,005 в час.
  Одно обновление занимает 15-30 минут и стоит несколько центов.
  Постоянный NAT стоил бы около $38 в месяц, это дороже всех серверов работы.
  Минус: обновления ставятся только вручную, их легко отложить. Если забыть `nat-down.sh`, шлюз продолжит списывать деньги.
  Дешевле можно сделать через бесплатный Gateway Endpoint для S3: репозитории Amazon Linux 2023 лежат в S3, и `dnf` сможет работать без NAT. Это стоит проверить в следующих работах.
- **Elastic IP у `app-server`.** Публичный адрес обычного экземпляра меняется после каждой остановки и запуска.
  Тогда пришлось бы каждый раз менять `APP_URL` в `.env` и адрес в браузере. Elastic IP даёт постоянный адрес.
  Он стоит $0,005 в час всегда, даже когда сервер остановлен (около $3,6 в месяц).
  Когда перед сервером появится балансировщик нагрузки (ALB), пользователи будут ходить на DNS-имя балансировщика.
  Тогда Elastic IP станет не нужен, а `app-server` можно будет перенести в приватную подсеть.
- Минус: база стоит в одной зоне `eu-central-1a`. При отказе зоны приложение остаётся без базы. Подсеть `private-b` пока пустая и оставлена под реплику.
- Минус: появился ещё один сервер, за который надо платить и который надо обновлять.
- Риск: загруженные файлы всё ещё лежат на диске `app-server` (`storage/uploads`). Их нужно будет перенести в S3.

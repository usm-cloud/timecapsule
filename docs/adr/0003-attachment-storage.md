# ADR-0003. Где хранить вложения пользователей

- Статус: принято
- Дата: 2026-10-25
- Закрывает риск из ADR-0002: файлы больше не лежат на диске `app-server`.

## Контекст

В ЛР2 и ЛР3 вложения капсул (картинки и PDF до 5 МБ) лежали в `storage/uploads` на диске `app-server`.
Приложение читало файл с диска и само отдавало его браузеру.
Файлы есть только на одном сервере. Его нельзя заменить новым или запустить рядом второй, не потеряв вложения.
Нужно решить, где хранить вложения, чтобы:

- сервер приложения можно было заменить без потери данных;
- несколько серверов приложения видели одни и те же файлы;
- посторонний не мог открыть чужой файл;
- случайное удаление можно было отменить;
- это стоило мало, на уровне учебного бюджета.

## Рассмотренные варианты

- **Диск EBS сервера приложения (как в ЛР3).**
  Ничего не нужно менять. Диск gp3 во Франкфурте стоит около $0,095 за ГБ в месяц, платим за весь размер диска, даже пустой.
  Диск живёт в одной зоне и подключается к одному экземпляру. Второй сервер этих файлов не видит.
  Защиту от удаления даёт только снимок диска, а восстановить из него один файл неудобно.
- **Общая файловая система Amazon EFS.**
  Её можно подключить к нескольким серверам сразу, в разных зонах. Код приложения почти не меняется: это та же папка.
  Хранение стоит около $0,36 за ГБ в месяц, в 15 раз дороже S3. Нужны mount target в каждой подсети и правило Security Group для NFS (порт 2049).
  Файл по-прежнему отдаёт сервер приложения, через свой канал и CPU. Версий файлов у EFS нет.
- **Бакет Amazon S3 (выбрано).**
  Хранение S3 Standard стоит около $0,0245 за ГБ в месяц, платим только за реальный объём.
  Объект хранится в нескольких зонах региона. Бакет виден любому серверу, у которого есть права.
  Есть версионирование и правила жизненного цикла. Браузер может скачать файл из S3 напрямую по подписанному URL, без нагрузки на сервер.
  Минус: нужен SDK и новый код модуля хранения. Работать с файлом как с обычным файлом на диске нельзя.

## Решение

Вложения хранятся в бакете `timecapsule-dev-uploads-semion` под префиксом `uploads/`.
Ключ объекта `uploads/<случайное имя>`, имя по-прежнему хранится в таблице капсул.
Приложение получает права через роль `timecapsule-dev-app-role` с политикой `timecapsule-dev-app-s3`: только `s3:GetObject`, `s3:PutObject` и `s3:DeleteObject` на `uploads/*`.
Ключей доступа в `.env` нет. SDK берёт временные учётные данные роли из метаданных экземпляра.
Бакет закрыт: `Block all public access`, `ACLs disabled`, политика бакета отклоняет запросы без HTTPS.

## Последствия

- **Как пользователь получает файл.** Приложение проверяет, что капсула открыта и пользователь имеет к ней доступ.
  Затем оно отвечает кодом 302 с подписанным URL на `GetObject`, и браузер скачивает файл из S3 напрямую.
  Ссылка действует 5 минут: срок записан в подписи (`X-Amz-Expires`), и S3 сам отклоняет ссылку после него.
  Ссылка также перестаёт работать, когда истекают временные учётные данные роли, которыми она подписана. Поэтому реальный срок может быть меньше 5 минут, но не больше.
  В ссылке подписаны тип содержимого и имя файла, поэтому браузер показывает картинку и сохраняет PDF под исходным именем.
- **Защита от случайного удаления.** В бакете включено версионирование. Удаление из приложения добавляет маркер удаления, а прежняя версия остаётся.
  У роли приложения нет `s3:DeleteObjectVersion` и `s3:ListBucketVersions`. Даже с украденными учётными данными приложения историю версий уничтожить нельзя.
- **Рост стоимости.** Правило `timecapsule-dev-noncurrent` переводит неактуальные версии в `Standard-IA` через 30 дней и удаляет их через 90 дней, оставляя 2 новейшие.
  Незавершённые загрузки частями удаляются через 7 дней.
  Маленькие файлы (меньше 128 КБ) в `Standard-IA` не переходят: там за них брали бы как за 128 КБ.
- **Несколько серверов и балансировщик.** Серверы приложения не хранят данных: на них только код и `.env`.
  Новый сервер запускается из образа, получает ту же роль и сразу видит все файлы. Балансировщик может отправить запрос на любой сервер.
  Скачивание файлов не проходит через серверы и балансировщик, поэтому они не тратят на него трафик и CPU.
  Нужно ещё убрать сессии с диска (`storage/sessions`) или включить на балансировщике привязку сессий (sticky sessions).
- Минус: запросы `app-server` к S3 идут через Internet Gateway. Позже их можно пустить через бесплатный Gateway Endpoint для S3.
- Минус: S3 о пользователях приложения ничего не знает. Проверка прав на капсулу остаётся в коде, ошибка в ней откроет чужой файл.
- Минус: бакет живёт в одном регионе `eu-central-1`. Чтобы пережить отказ региона, понадобится репликация в бакет другого региона (Cross-Region Replication).

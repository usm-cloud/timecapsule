## 3. Архитектура

![Архитектура](architecture.png)

Пользователи приходят по HTTP на Elastic IP `app-server` через Internet Gateway.
`app-server` стоит в `public-a` и находит базу по имени `db.timecapsule.internal` из приватной зоны Route 53.
`db-server` стоит в `private-a`, у него нет публичного адреса и маршрута в интернет.
Администратор заходит по SSH только на `bastion` в `public-b`, а оттуда на остальные серверы.
NAT Gateway показан пунктиром: он существует только во время обновления пакетов.

Решение о размещении базы: [ADR-0002](../adr/0002-database-placement.md).

## 5. Ответы на вопросы из заданий

**Задание 1. Почему доступных адресов не 256? Какие адреса занимает AWS? Сколько ещё подсетей `/24` поместится?**
В каждой подсети AWS забирает 5 адресов, поэтому экземплярам остаётся 256 − 5 = 251.
В `10.7.0.0/24` это: `.0` адрес сети, `.1` маршрутизатор VPC, `.2` DNS-сервер, `.3` запас AWS на будущее, `.255` широковещательный адрес (в VPC broadcast не работает, но адрес всё равно занят).
В `/16` помещается 256 подсетей `/24`. Я занял 4, значит, поместится ещё 252.

**Задание 2. Является ли подсеть `public-a` сейчас публичной?**
Нет. Подсеть публичная, только если в её таблице маршрутов есть маршрут `0.0.0.0/0` в Internet Gateway.
Сразу после создания подсеть связана с основной таблицей, где есть только маршрут `local`, а Internet Gateway ещё нет.
Название `public` ничего не меняет.

**Задание 3. Какой маршрут есть в обеих таблицах? Что он даёт? Куда уйдёт пакет из `private-a` на `8.8.8.8`?**
В каждой таблице есть маршрут `10.7.0.0/16` → `local`. Его нельзя удалить.
Он даёт связь между всеми подсетями VPC, в том числе из разных зон доступности.
Пакет на `8.8.8.8` не подходит под `10.7.0.0/16`, а других маршрутов в `private-rt` нет. Поэтому VPC его отбрасывает.

**Задание 4. Почему в `db-sg` источник `web-sg`, а не адрес или `10.7.0.0/16`?**
Правило с группой пускает любой сервер, у которого есть `web-sg`, какой бы адрес у него ни был.
Если веб-сервер пересоздадут или добавят второй, правило менять не нужно.
Диапазон `10.7.0.0/16` пустил бы к базе все серверы VPC, в том числе `bastion`. Это лишний доступ.

**Задание 5. Почему `db-server` не может скачать пакеты? Что добавить, чтобы он остался недоступен из интернета?**
У `db-server` нет публичного адреса, а в `private-rt` нет маршрута `0.0.0.0/0`. Пакеты в интернет просто отбрасываются.
Нужен NAT Gateway в публичной подсети и маршрут `0.0.0.0/0` на него в `private-rt`.
NAT пропускает только соединения, которые сервер открыл сам. Входящие соединения из интернета он не пропускает.

**Задание 6. Какой адрес вернул `checkip`? Почему это не адрес `db-server`?**
Команда вернула Elastic IP шлюза `timecapsule-dev-nat-a-eip`.
У `db-server` есть только приватный адрес `10.7.10.x`, в интернете он не работает.
NAT Gateway подменяет адрес отправителя на свой Elastic IP, а ответ возвращает обратно на `db-server`.

**Задание 6. Три механизма защиты базы. Что будет, если ошибиться в одном?**
Нет публичного адреса и маршрута в интернет: из интернета до сервера просто нельзя дойти.
`db-sg` решает, кто внутри VPC может подключиться к порту 5432: только серверы с `web-sg`.
`pg_hba.conf` решает, с каких адресов, к какой базе и под каким пользователем можно войти, и требует пароль.
Если ошибиться в одном из них, база всё ещё закрыта двумя другими. Например, если открыть `db-sg` для `0.0.0.0/0`, из интернета всё равно нет пути, а `pg_hba.conf` пустит только `10.7.0.0/24` с паролем.

**Задание 6. Почему PostgreSQL работает после удаления NAT? Что делать с обновлениями?**
NAT нужен только для соединений из VPC в интернет.
Приложение ходит к базе внутри VPC по маршруту `local`, и NAT для этого не нужен.
Для обновлений безопасности придётся снова поднять временный NAT Gateway, поставить обновления и удалить его. В Части 2 это делают скрипты `nat-up.sh` и `nat-down.sh`.

**Задание 7. Почему с `web-server` порт 5432 открыт, а с `bastion` нет?**
Маршрут между ними есть, но Security Group `db-sg` пускает на порт 5432 только серверы с группой `web-sg`.
У `bastion` группа `bastion-sg`, поэтому `db-sg` молча отбрасывает его пакеты, и проверка заканчивается по тайм-ауту.

**Задание 7. Почему `curl` на GitHub с `db-server` не проходит? Можно ли из интернета подключиться к 5432?**
Маршрут: в `private-rt` нет `0.0.0.0/0`, пакет на GitHub отбрасывается.
Адрес: у `db-server` нет публичного IP, поэтому ответ из интернета ему не вернуть.
Из интернета подключиться нельзя по тем же причинам: у сервера нет публичного адреса, в его подсети нет маршрута через Internet Gateway, а `db-sg` пускает только `web-sg`. Даже пакет, дошедший до сервера, отбросил бы `pg_hba.conf`.

**Задание 7. Network ACL: почему закрыты и SSH, и сайт? Почему с телефона работает? Почему номер меньше 100?**
Network ACL проверяет трафик на границе подсети, до Security Group. Правило запрещает весь трафик с моего адреса, на любой порт.
Network ACL по умолчанию связан со всеми подсетями VPC, поэтому закрыты и `bastion`, и `web-server`.
У телефона в мобильной сети другой внешний адрес, и правило под него не подходит.
Правила проверяются по возрастанию номера, и срабатывает первое подходящее. Правило `100` разрешает всё, поэтому запрет должен стоять раньше, с меньшим номером.

**Задание 7. Как по тегам найти ресурсы для удаления? Зачем тег `Owner` в личном аккаунте?**
В `Tag Editor` искать по `Project` = `timecapsule` (и `Lab` = `lab3`, если нужна одна работа). Список покажет всё, что нужно удалить.
`Owner` пригодится, когда аккаунт станет общим, например рабочим или учебным: по нему видно, кого спросить про ресурс.
Ещё по нему можно считать расходы на каждого человека. Привычка ставить его сразу проще, чем расставлять теги потом.

**Задание 8. Что содержит образ? Какие данные из ЛР2 оказались на `app-server`? Где сейчас база?**
Образ содержит снимок корневого диска EBS и описание для запуска: архитектуру и список дисков.
На `app-server` сразу оказались система, nginx, PHP-FPM, PostgreSQL, код в `/var/www/timecapsule`, `.env`, загруженные файлы, `~/deploy.sh` и сама база ЛР2.
Пока база работает локально на `app-server` (`localhost`), её копия пришла с образом.

**Задание 9. Почему Elastic IP нужен `app-server`, но не `bastion`? Сколько он стоит у остановленного сервера? Нужен ли он с балансировщиком?**
По адресу `app-server` ходят пользователи, и он записан в `APP_URL`, поэтому адрес должен быть постоянным.
На `bastion` хожу только я, и после запуска мне хватает обновить одну строку в `~/.ssh/config`.
Elastic IP стоит $0,005 в час всегда, даже у остановленного сервера: адрес закреплён за мной, и другим его выдать нельзя.
С балансировщиком Elastic IP не нужен: пользователи ходят на DNS-имя балансировщика, а сервер можно спрятать в приватную подсеть.

**Задание 10. Зачем новый сильный пароль, если 5432 закрыт Security Group?**
Security Group это только один уровень защиты. Если его настроят неправильно или взломают `app-server`, останется только пароль.
Старый пароль из ЛР2 лежит в `.env` и попал в образ, поэтому его нельзя считать секретным.

**Задание 11. Почему с `app-server` имя находится, а с моего компьютера нет? Что менять, если `db-server` пересоздадут?**
Имена приватной зоны отдаёт только DNS-сервер VPC (`10.7.0.2`), и только для VPC, связанных с зоной.
Мой компьютер спрашивает публичный DNS, а в нём зоны `timecapsule.internal` нет.
Если `db-server` пересоздадут, нужно изменить адрес в записи `A` для `db`. `.env` и приложение менять не нужно.

**Задание 12. Где лежат файлы капсул? Что с ними будет, если удалить `app-server`?**
Файлы лежат в `/var/www/timecapsule/storage/uploads` на корневом диске `app-server`. Они приехали вместе с образом.
При удалении экземпляра корневой диск по умолчанию удаляется, и файлы пропадут.
В базе останутся записи о файлах, которых уже нет. Чтобы этого избежать, файлы надо хранить в S3.

**Задание 13. Почему в `deploy.sh` ничего не пришлось менять?**
Скрипт работает на самом сервере: берёт код из GitHub, ставит зависимости и перезапускает PHP-FPM.
Адрес базы он берёт из `.env`, а не из кода.
Изменился только путь до сервера, а его задаёт `~/.ssh/config` (`ProxyJump bastion`). Поэтому команда выглядит так же просто: `ssh app ./deploy.sh`.

**Задание 13. Что показал `/health` при остановленной базе? Изменился ли адрес `db-server`?**
`/health` ответил с кодом 500 и `"db":"error"`, потому что не смог подключиться к базе. Ответ пришёл с задержкой: приложение ждало соединения.
Приватный адрес после остановки и запуска не изменился, он закреплён за сетевым интерфейсом сервера.
Поэтому запись `db.timecapsule.internal` осталась верной, и приложение заработало само.

**Задание 13. Почему Elastic IP освобождают только после удаления NAT Gateway?**
Пока шлюз существует, адрес к нему привязан, и AWS не даст освободить привязанный адрес.
Шлюз отпускает адрес только после перехода в `Deleted`, иногда ещё через минуту. Поэтому `nat-down.sh` ждёт удаления и повторяет попытку.

## 6. Контрольные вопросы

**1. Как проходит запрос от браузера до базы? Какие маршруты и фильтры он проходит?**
Браузер шлёт запрос на Elastic IP. Internet Gateway заменяет его на приватный адрес `app-server`.
Network ACL подсети `public-a` пропускает трафик, затем `web-sg` пропускает порт 80. nginx передаёт запрос в PHP-FPM.
PHP узнаёт адрес `db.timecapsule.internal` у DNS VPC и идёт на `10.7.10.x:5432` по маршруту `local`.
Дальше Network ACL `private-a`, `db-sg` (источник `web-sg`) и `pg_hba.conf` (адрес из `10.7.0.0/24`, пользователь, пароль). Ответ идёт обратно тем же путём, Security Group пропускает его сама.

**2. Злоумышленник знает приватный IP `db-server`. Что ему нужно, чтобы подключиться?**
Сначала попасть внутрь VPC, потому что из интернета маршрута к этому адресу нет.
Причём попасть на сервер с группой `web-sg` в подсети `public-a`, то есть фактически взломать `app-server`.
Потом ему нужны имя пользователя и пароль базы. Другой путь: украсть доступ к аккаунту AWS и поменять сеть.

**3. Чем временный NAT лучше постоянного? Какие неудобства?**
Он стоит центы вместо примерно $38 в месяц. Большую часть времени у базы вообще нет выхода в интернет, и украденные данные через него не вывести.
Неудобства: обновления надо ставить руками, ждать несколько минут, пока шлюз создаётся, и не забыть его удалить.
Без шлюза база не получает обновления сама.

**4. Как пережить отказ зоны `eu-central-1a`? Чего не хватает?**
Не хватает второго `app-server` в `public-b` и балансировщика нагрузки (ALB) перед обоими серверами.
Не хватает копии базы в `private-b` с переключением при отказе, например RDS Multi-AZ.
Загруженные файлы надо вынести в S3, чтобы их видели оба сервера. Если нужен NAT, его нужно поставить в каждую зону.
